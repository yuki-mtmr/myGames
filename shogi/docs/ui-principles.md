# 将棋訓練アプリ UI 成立条件(10 項目)

game-lab の `docs/principles.md`(Three.js ミニゲーム成立条件)を将棋訓練アプリの
対局・感想戦・訓練 UI 文脈に翻訳したもの。詳細な設計根拠は
`docs/design-principles.md`(設計原則1〜10)を参照。

## 1. 画面遷移は明示的な FSM で管理する

`対局 / 感想戦 / ダッシュボード / ドリル` の 4 画面 + モーダル(設定・成り確認)を
enter/exit ライフサイクル付きの状態機械として扱い、タブ切替時のイベントリスナー
二重登録・評価値エンジンの多重起動を構造的に防ぐ。ハッシュルーティング
(`#play` `#review` 等)は状態と 1:1 対応させる。

## 2. 入力の即応と取りこぼしゼロ

駒のクリック/タップ → 移動可能マスのハイライトは 1 フレーム以内に反映し、
成り確認ダイアログや持ち駒打ち込みの選択操作も入力バッファで取りこぼさない。
盤面操作(離散的なマス座標)と着手アニメーション(連続的な補間)を分離する。
将棋ウォーズはこの反応速度をアプリの基本体験として重視している(未検証だが推測)。

## 3. 10 秒オンボーディング

「これは何のアプリか」をテキストで説明せず、対局画面が既存将棋ソフトの共通規約
(駒台位置・評価値バー・最終手ハイライト)に完全準拠することで、初回操作から
迷いなく指せる状態を作る(design-principles.md 原則1)。

## 4. 終局から次の行動まで 1 操作(即時リスタート相当)

終局 →「感想戦へ」or「もう一局」への遷移をワンクリックで提示する。
感想戦の再演モードでも「不正解→再挑戦」は即座に次の入力を受け付け、
結果画面の演出で再挑戦を遅らせない(design-principles.md 原則4のエラー修正学習を
妨げない速度で提供)。ぴよ将棋の感想戦ボタン導線が近い設計と考えられる(未確認)。

## 5. Juice は応答性の上に載せる

駒音・着手アニメーション・最終手ハイライト・悪手トーストの演出は、
盤面操作の即応性(項目2)と評価値/判定表示の正確性が成立した後に追加する。
特に「疑問手?」トーストは正解手を隠す設計(想起練習の妨げ防止)が機能面の要件であり、
演出はその制約を壊さない範囲に留める。

## 6. 判定・スケジューリングはデータ駆動にする

悪手判定閾値・癖認定閾値・FSRS パラメータ・目標正答率(85%)は
`src/config/trainingConfig.js` に集約し、コードにハードコードしない
(design-principles.md 原則10)。難易度曲線に相当するドリル出題順は
FSRS が動的に選択する。

## 7. パフォーマンス予算: 評価値計算は操作をブロックしない

やねうら王(WASM)/内蔵 Minimax の評価値計算は非同期(Web Worker 等)で行い、
盤面操作・タブ切替の 60fps 相当の応答性を落とさない。感想戦の局面再生や
評価値グラフ描画も同様に UI スレッドを塞がない。

## 8. セッションは短く、継続は「壊れない」設計にする

1 ドリルセッション 10〜15 分で「今日の分は完了」と明示的に終わる
(無限スクロール的な引き止めをしない)。ヒートマップは連続日数でなく
累積努力を可視化し、休んでも進捗が消えない(design-principles.md 原則8)。
Duolingo 系アプリのストリーク疲弊を反面教師にした設計(傍証: freeze でチャーン減、
未検証の一般化)。

## 9. テクスチャレスでも将棋盤としての完成度を作る

盤・駒は画像アセットなしでも CSS/Canvas のグラデーション・コントラスト配色で
視認性の高い盤面を構成できる(3D モードは対局画面のみのオプション)。
判定マーク(疑問手=橙/悪手=赤/大悪手=濃赤)は装飾ではなく情報であり、
視界・操作性を阻害しない配置にする。

## 10. 「動く」ではなく「意図通り」を検証する

console エラー 0 は必要条件に過ぎない。悪手判定・勝率換算・FSRS 出題が
仕様通りの局面/数値を返しているかをスクリーンショットと実データで確認し、
弱い画面だけを狙い撃ちで修正する。将棋クエストの棋神解析のような
「それらしく動くが判定基準が非公開/不透明」な状態を避け、閾値の出典を明示する
(design-principles.md 原則2)。
